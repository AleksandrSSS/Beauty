# План: виправлення прев'ю ротації у формі майстра (адмінка)

Актуально на **2026-09-08**. Стосується блоку «Так виглядатиме графік…» у формі майстра
(вкладка «Майстри» адмін-панелі). Три правки: (№1) прев'ю рахувати **від якірної дати**,
(№2) формат дати **ДД-ММ**, (№3) показувати блок як **календарну сітку** (компонент `BookingCalendar`,
як на сторінці бронювання), а не ряд чіпів.

> ⚠️ Це **план**, а не реалізація. Нічого не застосовано. Реалізовувати лише після команди «виконуй».

> **Важливо:** правка №3 (перехід на календар) **поглинає** №1 і №2 у клієнтській частині — календар
> стартує від `from={rotationAnchor}` (закриває №1 на клієнті) і показує лише число дня в комірці
> (проблема формату ММ-ДД зникає, №2 стає неактуальним для цього блоку). Серверна частина №1
> (`PreviewRotation` від якоря) все одно потрібна, щоб дані відповідали календарю. Деталі — §6.

---

## 1. Вимоги (від користувача)

1. **№1 — прев'ю від якірної дати.** Зараз прев'ю показує 15(+) днів **від сьогодні**, а має показувати
   графік **від `rotationAnchor`** (перший робочий день зміни / понеділок робочого тижня). Рішення користувача:
   **варіант B — від якірної дати**.
2. **№2 — формат дати ДД-ММ.** Зараз відображається `ММ-ДД` (напр. `09-08`), має бути `ДД-ММ` (`08-09`).
   *(Стає неактуальним у разі №3 — календар показує лише число дня.)*
3. **№3 — вигляд календаря.** Блок «Так виглядатиме графік…» має виглядати як **календарна сітка Пн–Нд**
   (той самий компонент `BookingCalendar`, що використовується при створенні бронювання), а не як ряд чіпів
   `ДД-ММ ✅/🏖`.

---

## 2. Що НЕ є дефектом (перевірено — не чіпати)

**Логіка ротації `RotationHelper.WorksOn` — коректна.** Перевірено вручну для TwoTwo з якорем 01.10.2026:
формула `(((day.DayNumber - anchor.DayNumber) % 4) + 4) % 4 < 2` дає рівно той графік, що описав користувач
(08.09 ✅, 09.09 🏖, 10.09 🏖, 11.09 ✅, 12.09 ✅, …). Позначки ✅/🏖 правильні. **Розрахунок ротації
(`RotationHelper`, `WorksOn`) НЕ міняти** (§4.2 AGENTS.md — єдине джерело правди ротації).

Проблема №1 — **не в розрахунку**, а в тому, від якої дати починається вікно прев'ю (`today` замість `anchor`).

---

## 3. Поточний стан (факти з коду)

### №1 — старт прев'ю

Файл: `server/Services/ScheduleService.cs`, метод `PreviewRotation`:
```csharp
public List<MasterDayDto> PreviewRotation(RotationType type, DateOnly anchor)
{
    var probe = new Master { RotationType = type, RotationAnchor = anchor };
    var today = clock.TodayInSalon;                       // ← старт від СЬОГОДНІ
    return Enumerable.Range(0, WindowDays + 1)            // ← WindowDays=28 → 29 днів
        .Select(i => today.AddDays(i))
        .Select(day => new MasterDayDto(day, RotationHelper.WorksOn(probe, day), null, null, []))
        .ToList();
}
```
- Прев'ю починається від `clock.TodayInSalon`, а не від `anchor`.
- Рахується `WindowDays + 1 = 29` днів (не «15», як каже підпис у UI — див. §5).

Виклик: `AdminController.RotationPreview` (`POST /api/admin/rotation-preview`) → `schedule.PreviewRotation(rt, dto.RotationAnchor)`
→ повертає `[{ date, isWorking }]`. Ендпоінт не міняється.

### №2 — формат дати

Файл: `client/src/pages/Admin.tsx`, рендер прев'ю (рядок ~265):
```tsx
{rotPreview.map(d => (
  <span key={d.date} className="slot">{d.date.slice(5)} {d.isWorking ? '✅' : '🏖'}</span>
))}
```
- `d.date` = `"2026-09-08"` (YYYY-MM-DD, салонна дата з сервера).
- `.slice(5)` → `"09-08"` = **ММ-ДД**. Потрібно `"08-09"` = ДД-ММ.

Підпис поряд (рядок ~262): `<label>Так виглядатиме графік на 15 днів:</label>` — число «15» не відповідає
реальним 29 дням (див. §5).

## 4. Зміни (детально)

### 4.1. №1 — прев'ю від якірної дати (сервер)

Файл: `server/Services/ScheduleService.cs`, `PreviewRotation`:
- Замінити старт `today` на `anchor`:
  ```csharp
  var probe = new Master { RotationType = type, RotationAnchor = anchor };
  return Enumerable.Range(0, WindowDays + 1)
      .Select(i => anchor.AddDays(i))                  // ← від якоря, а не від сьогодні
      .Select(day => new MasterDayDto(day, RotationHelper.WorksOn(probe, day), null, null, []))
      .ToList();
  ```
- `clock.TodayInSalon` у цьому методі більше не використовується — прибрати рядок `var today = ...`.
- `RotationHelper.WorksOn` **не чіпати**.
- Наслідок: для TwoTwo з якорем 01.10 прев'ю почнеться з `01.10 ✅ 02.10 ✅ 03.10 🏖 04.10 🏖 …`
  (перший робочий день зміни — перший у списку). Для Weekly — від понеділка-якоря.

> Форма відповіді ендпоінта (`[{ date, isWorking }]`) не змінюється — клієнт правити не треба (крім формату №2).

### 4.2. №2 — формат ДД-ММ (клієнт) — *лише якщо №3 НЕ роблять*

> Якщо реалізується №3 (календар, §4.3) — цю правку **пропустити**: календар не показує `ММ-ДД` взагалі,
> лише число дня в комірці. §4.2 актуальна тільки як запасний варіант, коли лишаємо ряд чіпів.

Файл: `client/src/pages/Admin.tsx`, рядок рендеру прев'ю:
```tsx
{rotPreview.map(d => (
  <span key={d.date} className="slot">{d.date.slice(8, 10)}-{d.date.slice(5, 7)} {d.isWorking ? '✅' : '🏖'}</span>
))}
```
- `d.date.slice(8,10)` = день, `d.date.slice(5,7)` = місяць → `ДД-ММ` (`"08-09"`).
- Це рядкова перестановка над готовою салонною датою `YYYY-MM-DD` (не парсинг `Date`), тому **не порушує**
  §4.1 AGENTS.md (заборона `.slice(0,10)`/`new Date(...)` стосується отримання салонної дати з UTC-мітки;
  тут дата вже салонна, лише переставляємо частини для показу).

### 4.3. №3 — блок як календарна сітка (`BookingCalendar`) — **основний варіант**

**Мета:** показувати прев'ю ротації тим самим календарем Пн–Нд, що й на сторінці бронювання, замість ряду чіпів.

**Компонент уже існує і підходить:** `client/src/components/BookingCalendar.tsx`. Релевантні пропси
(факти з коду компонента):
- `availableDates: Set<string>` — дати (YYYY-MM-DD), позначені як активні (тут = **робочі дні** прев'ю).
- `mode: 'schedule' | 'booking'` — впливає лише на легенду; для прев'ю ротації — `'schedule'`
  (легенда «робочий день / вихідний»).
- `from?: string` — перший день вікна; **тут = `rotationAnchor`** → закриває №1 на клієнті.
- `windowDays?: number` — глибина; дефолт 28.
- `selected: string | null`, `onSelect: (d) => void` — **обов'язкові** пропси вибору.
- `workingDates?`, `labels?` — опційні.

**Проблема:** прев'ю — це **лише перегляд**, у ньому нічого не обирається, а `BookingCalendar` малює
комірки як клікабельні `<button disabled={!available}>` і вимагає `selected`/`onSelect`. Тому потрібен
**режим «тільки перегляд»** (read-only). Два варіанти реалізації (узгодити, §5):

- **3A (мінімальна зміна, без правки компонента):** використати `BookingCalendar` як є, передавши
  `selected={null}` і `onSelect={() => {}}` (no-op). Робочі дні будуть клікабельними візуально, але клік
  нічого не робить. Швидко, але семантично це «вибір, що нічого не обирає».
- **3B (акуратніше, невелика правка компонента):** додати в `BookingCalendar` опційний проп
  `readOnly?: boolean`. Коли `true`: `onSelect`/`selected` необов'язкові, усі комірки `disabled`
  (не клікабельні, без `--sel`), легенда лишається. `Booking.tsx`/`MasterSchedule.tsx` не зачіпаються
  (проп опційний, дефолт `false`). **Пропозиція: 3B** — чистіше, і календар стає перевикористовним для
  будь-яких read-only прев'ю.

**Використання в `Admin.tsx`** (блок прев'ю замість ряду `.slot`-чіпів):
```tsx
<label>Графік роботи (прев'ю від дати початку):</label>
<BookingCalendar
  mode="schedule"
  from={mstForm.rotationAnchor}
  availableDates={new Set(rotPreview.filter(d => d.isWorking).map(d => d.date))}
  selected={null}
  onSelect={() => {}}
  // 3B: readOnly
/>
```
- `availableDates` = робочі дні з `rotPreview` (`isWorking === true`).
- `from = mstForm.rotationAnchor` — календар почне з місяця якоря; сам розрахунок статусів лишається
  серверний (`rotPreview`), календар лише розкладає їх по сітці.
- Імпорт `BookingCalendar` уже може бути відсутнім у `Admin.tsx` — додати.

**Наслідок для №1/№2:**
- №1: `from={rotationAnchor}` на клієнті + серверний `PreviewRotation` від якоря (§4.1) дають узгоджене
  вікно від якоря. **Серверна правка §4.1 все одно потрібна**, щоб `rotPreview` містив саме дні від якоря
  (інакше `availableDates` матиме дати від сьогодні, а календар — сітку від якоря → неспівпадіння).
- №2: у календарі формату `ММ-ДД` немає → §4.2 не потрібна.

**Стилі:** класи календаря (`.calendar`, `.cal-day`, `.calendar__grid` тощо) вже є в `styles.css`
(використовуються бронюванням). Нічого нового додавати не треба; за потреби read-only вигляду —
доповнити `styles.css` (тільки додавання, §6 AGENTS.md).

## 5. Відкриті деталі (узгодити)

### 5.1. Read-only режим календаря (№3)
Варіант **3A** (no-op `onSelect`, без правки компонента) чи **3B** (додати проп `readOnly` у
`BookingCalendar`)? Пропозиція: **3B** — комірки не клікабельні, семантично коректно, інші сторінки
не зачіпаються (проп опційний). Див. §4.3.

### 5.2. Підпис «на 15 днів»
Реально прев'ю показує `WindowDays + 1 = 29` днів. Число «15» у підписі (`Admin.tsx`) не відповідає дійсності.
Якщо переходимо на календар (№3), підпис усе одно варто зробити правдивим. Варіанти:
- **A.** Підпис «Графік роботи (прев'ю від дати початку, 4 тижні):» — узгодити з `WindowDays=28`. Пропозиція.
- **B.** Скоротити прев'ю до 15 днів (`Enumerable.Range(0, 15)`) — збігається з поточним підписом.
- **C.** Не чіпати підпис.

> Поза прямою вимогою користувача. Пропозиція: **A**. Не робити без підтвердження.

## 6. Порядок реалізації

**Основний шлях (з календарем №3):**
1. **С1. Сервер** `PreviewRotation`: старт від `anchor` (§4.1) — потрібен, щоб дані відповідали календарю.
2. **К1. (за 3B) `BookingCalendar`**: додати опційний проп `readOnly` (§4.3, §5.1).
3. **К2. `Admin.tsx`**: замінити ряд чіпів на `<BookingCalendar mode="schedule" from={rotationAnchor} …>` (§4.3);
   імпорт компонента.
4. **(опц.) К3.** підпис зробити правдивим (§5.2, лише якщо узгоджено).
5. **П. Перевірка** (§7).

> Правку №2 (§4.2) при цьому шляху **не роблять** — формат ММ-ДД зникає разом із чіпами.

**Запасний шлях (без календаря, лишаємо чіпи):** С1 (§4.1) + §4.2 (формат ДД-ММ) + §5.2. Тільки якщо
відмовляємось від №3.

## 7. Перевірка (перед «готово», §12 AGENTS.md)

1. `dotnet build server` — без нових warning'ів.
2. `cd client; npm run build` — tsc + vite без помилок.
3. У формі майстра **TwoTwo**, якір 01.10.2026 → **календар** показує сітку від жовтня; `01.10` і `02.10`
   позначені робочими (активний стиль), `03.10`/`04.10` — вихідні (disabled/off), далі чергування 2/2.
4. У формі майстра **Weekly**, якір-понеділок → календар: робочий тиждень Пн–Нд активний, наступний —
   вихідний, і чергується.
5. Блок виглядає як **календарна сітка Пн–Нд** (класи `.calendar`/`.cal-day`), а не ряд чіпів; формату
   ММ-ДД немає (в комірці лише число дня).
6. Зміна `rotationType`/`rotationAnchor` у формі перераховує прев'ю і **зсуває старт календаря** (`from`
   оновлюється; реактивність `useEffect` + проп `from` збережена).
7. **Регресія бронювання:** `BookingCalendar` на `/booking` і `/masters/:id` працює як раніше (вибір дати,
   клікабельні слоти) — проп `readOnly` (3B) опційний і не активний там.
7. Логіка ротації не змінилась деінде: слоти (`/api/booking/slots`), графік майстра
   (`/api/catalog/masters/{id}/schedule`) працюють як раніше (перевірити на межі — вони від `today`, не від якоря).

## 8. Обмеження / застереження

- `RotationHelper.WorksOn` — **єдине джерело правди ротації** (§4.2 AGENTS.md). Не дублювати й не міняти.
- Правка №1 стосується **лише прев'ю** у формі майстра. Слоти й публічний графік майстра рахуються від
  `today` (вікно бронювання) — їх **не чіпати**, вони працюють правильно.
- Формат ДД-ММ — суто відображення; салонна дата з сервера лишається `YYYY-MM-DD`.
```
