## S1 — Автентифікація (критично, блокер прода)

Найсерйозніший блок: увесь логін вразливий до брутфорсу. Виконувати повністю, всі задачі пов'язані.

### S1-1. Посилити OTP-код
- **Де:** `AuthController.cs` (`CodeChars`, генерація в `RequestCode`), `Models/Entities.cs` (`VerificationCode`).
- **Що:** код — **6 цифр** з повного діапазону `0–9` (10⁶ = 1 000 000 комбінацій) замість 4 символів з `"123456789"` (6561).
- **Критерій:** `request-code` генерує 6-значний код; наявні коди в БД не ламають логіку.

### S1-2. Зберігати код як хеш, а не відкритим текстом
- **Де:** `VerificationCode` (нове поле `CodeHash`, прибрати/задепрекейтити `Code`), `AuthController.VerifyCode`.
- **Що:** зберігати `SHA256(code + salt)` (salt — per-row або з конфігу). Порівняння — за хешем.
- **Міграція:** `dotnet ef migrations add AddVerificationCodeHash --project server` (додати колонку, старі рядки — прострочені/очищені). Дотримуватись §7 AGENTS: не редагувати застосовані міграції, переглянути DDL через `migrations script`.
- **Критерій:** у таблиці `verification_codes` немає читабельного коду; `verify-code` працює.

### S1-3. Ліміт спроб на verify-code
- **Де:** `VerificationCode` (нове поле `AttemptCount`), `AuthController.VerifyCode`.
- **Що:** інкремент `AttemptCount` при кожній невдалій перевірці; при `> 5` код вважається спаленим (переривати навіть при правильному значенні).
- **Критерій:** 6-та спроба по одному коду завжди відхиляється.

### S1-4. Rate-limiting
- **Де:** `Program.cs` (`AddRateLimiter` + `UseRateLimiter`), атрибути на діях `AuthController`.
- **Що:**
  - `request-code`: 5 запитів / 10 хв на телефон+IP.
  - `verify-code`: обмеження на IP (напр. 10/10 хв).
  - `admin-login`: 5 / 15 хв + тимчасовий lockout.
- **Критерій:** перевищення ліміту повертає 429 у форматі `{ "error": "..." }` (узгодити з §4.5 AGENTS).

### S1-5. Прив'язка verify до конкретного запиту (RequestId)
- **Де:** `AuthController.RequestCode`/`VerifyCode`, `VerificationCode` (поле `RequestId`), `client/src/api.ts` + `types.ts` + сторінка логіну.
- **Що:** `request-code` повертає `requestId`; `verify-code` вимагає його. Профіль (`Name`/`Contact`) оновлюється **тільки** в межах свого запиту — усунути перезапис чужого профілю будь-ким із валідним кодом.
- **Критерій:** без коректного `requestId` verify не проходить; чужий профіль не переписати.

### S1-6. Гартування JWT
- **Де:** `Program.cs`, `JwtService.cs`.
- **Що:**
  - Перевірка довжини `Jwt:Key` ≥ 32 байт при старті (кидати виняток, як уже робиться при відсутності ключа).
  - Скоротити access-токен (напр. 15 хв) + refresh-токен у httpOnly-cookie з можливістю відкликання.
  - **Примітка:** refresh-токени = задача P0-6 роадмапу, вона поза активним `masters-feature-plan`. Якщо обсяг великий — виконати перевірку довжини ключа зараз (S1-6a), а refresh винести окремим кроком (S1-6b) з підтвердженням користувача.
- **Критерій:** сервер не стартує з коротким ключем; `POST /api/auth/admin-login` далі повертає 200 (перевірка BCrypt-хеша, §12 AGENTS).

## S2 — Надійність (major)

### S2-1. Global fallback authorization policy
- **Де:** `Program.cs`.
- **Що:** `FallbackPolicy = RequireAuthenticatedUser` — усе закрите за замовчуванням, публічні ендпоінти лишаються з явним `[AllowAnonymous]` (`request-code`, `verify-code`, `admin-login`, гостьове `booking/create` + `/confirm`, публічний каталог).
- **Ризик:** треба пройтися по всіх контролерах і переконатись, що потрібні публічні дії мають `[AllowAnonymous]` — інакше зламається каталог/бронювання.
- **Критерій:** захищені ендпоінти без токена → 401; усі публічні шляхи (каталог, слоти, гостьове бронювання) працюють без токена.

### S2-2. Централізована обробка помилок і security headers
- **Де:** `Program.cs`, можливо middleware/`Controllers`.
- **Що:** `UseExceptionHandler` з ProblemDetails у форматі `{ "error": "..." }` (узгодити з §4.5), без стектрейсу в non-Development; базові security headers (`X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, тощо).
- **Критерій:** неопрацьований виняток → 500 з тілом `{ "error": ... }`, без стектрейсу.

### S2-3. Пагінація важких вибірок
- **Де:** `AdminController.Appointments` (і за потреби `AccountController.Appointments`).
- **Що:** параметри `page`/`pageSize` (+ опційно `from`/`to`), замість `Include`×3 + повний `ToList()`.
- **Контракт:** нові параметри DTO додавати **лише останніми** (§5 AGENTS). Клієнт (`Admin.tsx`) оновити відповідно.
- **Критерій:** ендпоінт повертає сторінку, а не весь список; UI адмінки відображає записи.

### S2-4. Прибрати dead code
- **Де:** `AuthController.AdminLogin` — невикористовувана змінна `adminPhone`.
- **Критерій:** `dotnet build server` без нових warning'ів; поведінка логіну незмінна.

## Перевірка перед «готово» (за §12 AGENTS)

1. `dotnet build server` — без нових warning'ів.
2. `cd client; npm run build` — tsc + vite без помилок.
3. Якщо торкався авторизації/пакетів — `POST /api/auth/admin-login` повертає 200.
4. Якщо торкався слотів/бронювання — обидва режими `POST /api/booking/slots` дають ту саму форму відповіді, повний цикл бронювання проходить.
5. Якщо торкався схеми — `dotnet ef migrations list` + перевірка колонок у psql.
6. Стверджувати «працює» лише про те, що реально запускав.
