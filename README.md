# Beauty Salon — сайт салону (цирюльня + манікюр)

Тестовий проєкт: запис до майстра з підтвердженням кодом, особистий кабінет, адмін-панель.

## Стек
- **Backend**: ASP.NET Core 10 + EF Core 10 + PostgreSQL 16
- **Frontend**: React 18 + Vite 5 + TypeScript
- **Контейнеризація**: Docker (postgres + server + nginx), єдина точка входу через nginx
- Авторизація: JWT (клієнти — за кодом з повідомлення, адмін — логін/пароль) + refresh-токени в httpOnly-cookie

---

# Запуск

Проєкт можна підняти двома способами:

| Режим | Коли | Точка входу |
|---|---|---|
| **A. Docker-стек** | «як на справжньому хості», усе в контейнерах | http://localhost:8080 |
| **B. Локальний dev** | розробка з hot-reload | http://localhost:5173 |

---

## A. Docker-стек (рекомендовано для перевірки «як на хості»)

Піднімає **всі три сервіси** в контейнерах: PostgreSQL, бекенд (ASP.NET Core) і nginx, що віддає зібраний фронтенд і проксує API. Клієнт і API — на одному origin, тому CORS не задіяний, а refresh-cookie працює без застережень.

```
браузер → http://localhost:8080 → nginx (web)
   ├── /            → статика React (production build)
   ├── /api/...     → server:8080 (ASP.NET Core)
   └── /uploads/... → server:8080 (фото майстрів)
                         server → postgres:5432
```

### Передумови
- Docker Desktop / Docker Engine з плагіном `docker compose`.

### Крок 1. Секрети — кореневий `.env`
Скопіюйте шаблон і заповніть значення (файл у git **не** потрапляє):

```powershell
Copy-Item .env.example .env
```

Обов'язкові ключі в `.env`:

| Ключ | Призначення | Як згенерувати |
|---|---|---|
| `POSTGRES_PASSWORD` | пароль PostgreSQL | будь-який; має збігатися з паролем, яким ініціалізовано том БД |
| `JWT_KEY` | ключ підпису JWT, **≥32 байти** | `openssl rand -base64 48` |
| `ADMIN_PASSWORD` | пароль адміна (лише для порожньої БД) | `openssl rand -base64 18` |
| `CODE_SALT` | сіль для хешування OTP-кодів | `openssl rand -base64 24` |

> ⚠️ Якщо `JWT_KEY` коротший за 32 байти — сервер не стартує (це навмисна перевірка безпеки).

### Крок 2. Збірка і запуск

```powershell
docker compose up -d --build
```

Перевірити стан і логи:

```powershell
docker compose ps
docker compose logs -f server
```

Відкрити застосунок: **http://localhost:8080**

Міграції БД застосовуються **автоматично** при старті бекенда (`DbInitializer.Migrate()`); демо-дані (послуги, майстри, адмін) створюються на порожній БД.

### Зупинка

```powershell
docker compose down        # зупинити (том БД і фото зберігаються)
docker compose down -v     # ❌ НЕ використовувати без потреби — знищить дані БД і фото
```

### Оновлення після зміни коду

```powershell
docker compose up -d --build server   # перезібрати лише бекенд
docker compose up -d --build web      # перезібрати лише фронтенд
```

## B. Локальний dev (hot-reload)

Тут у контейнері працює **лише PostgreSQL**, а бекенд і фронтенд запускаються локально.

### Крок 1. PostgreSQL

```powershell
docker compose up -d postgres
```

### Крок 2. Секрети бекенда — user-secrets
Пароль адміна і ключ JWT у dev тримаються в **user-secrets** (не в `appsettings.json`):

```powershell
cd server
dotnet user-secrets set "Jwt:Key" "<ключ щонайменше 32 байти>"
dotnet user-secrets set "Admin:Password" "<пароль>"
```

### Крок 3. Backend (порт 5000, потрібен .NET 10 SDK)

```powershell
dotnet run --project server
```

### Крок 4. Frontend (порт 5173)

```powershell
cd client
npm install
npm run dev
```

Клієнт звертається до API за `VITE_API_URL` (див. `client/.env`, дефолт `http://localhost:5000`); Vite додатково проксує `/api` і `/uploads`.

---

## Доступи
- **Адмін**: телефон `+380000000000`, пароль — зі свого `.env` (`ADMIN_PASSWORD`) або user-secrets (`Admin:Password`).
  - ⚠️ Пароль адміна створюється **лише при першому заповненні порожньої БД**. Якщо БД уже містить адміна (сід ідемпотентний), зміна `ADMIN_PASSWORD` на нього не вплине.
- **Клієнти**: вхід за номером телефону + код підтвердження (у dev-режимі код повертається в полі `devCode`; у Production — ні).

# Деплой у прод на хост

Нижче — розгортання docker-стеку на реальному Linux-сервері (VPS/виділений хост). Кроки, які вимагають ваших рішень (домен, спосіб TLS), позначені явно.

## 1. Підготовка хоста
- Встановіть Docker Engine + `docker compose` (офіційна інструкція Docker для вашого дистрибутиву).
- Відкрийте у фаєрволі порти **80** і **443** (для HTTPS). Порт `5432` (PostgreSQL) назовні **не відкривати**.
- Скопіюйте проєкт на хост (git clone або rsync).

## 2. Прод-секрети (`.env`)
Згенеруйте **нові** значення просто на хості — не переносьте dev-секрети:

```bash
{
  echo "POSTGRES_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"
  echo "JWT_KEY=$(openssl rand -base64 48)"
  echo "ADMIN_PASSWORD=$(openssl rand -base64 18 | tr -d '/+=')"
  echo "CODE_SALT=$(openssl rand -base64 24)"
} > .env
chmod 600 .env
```

> На **порожній** прод-БД цей `ADMIN_PASSWORD` і стане паролем адміна. Збережіть його в менеджері секретів.

## 3. HTTPS (обов'язково для прода)
Поточний `docker-compose.yml` віддає стек по HTTP на порту 8080. Для прода потрібен TLS. Оберіть один зі способів:

**Варіант 1 — reverse-proxy з автосертифікатами (проста рекомендація).**
Поставте перед стеком [Caddy](https://caddyserver.com/) або Traefik з Let's Encrypt: вони самі отримують і продовжують сертифікат для вашого домену і проксують на сервіс `web`. Тоді у compose достатньо не публікувати `web` назовні, а віддати його проксі.

**Варіант 2 — nginx + certbot** на хості перед контейнером `web`.

**Варіант 3 — TLS на зовнішньому балансері** (хмарний LB), якщо він у вас уже є.

> Реалізацію TLS-проксі не додано в репозиторій навмисно — вибір залежить від вашої інфраструктури. Опишіть бажаний спосіб, і його можна додати в `docker-compose.yml`.

## 4. Прод-налаштування застосунку
У проді змініть/додайте env-змінні сервісу `server` (у `docker-compose.yml` або override-файлі):

| Змінна | Значення для прода | Навіщо |
|---|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` | вже задано — приховує деталі помилок, вимикає `devCode` |
| `Jwt__RefreshCookieSecure` | `true` | refresh-cookie тільки по HTTPS |
| `Cors__AllowedOrigins__0` | `https://ваш-домен` | дозволений origin клієнта |
| `Salon__TimeZone` | напр. `Europe/Kyiv` | таймзона салону |

`nginx.conf` клієнта задає `client_max_body_size` для фото — за потреби узгодьте з лімітом `Uploads:MaxFileSizeBytes` бекенда.

## 5. Персист ключів DataProtection (рекомендовано)
Бекенд попереджає, що ключі DataProtection зберігаються в контейнері й губляться при його перестворенні. Щоб уникнути цього, змонтуйте том на `/root/.aspnet/DataProtection-Keys` для сервісу `server`. (Поточну авторизацію на JWT це не ламає, але прибирає warning і робить поведінку стабільною між релізами.)

## 6. Реальні нотифікації
За замовчуванням канали працюють у **MOCK**. Для реальної доставки задайте у `.env` / env сервісу `server` (див. розділ «Канали нотифікацій» нижче): Twilio (SMS/WhatsApp), SMTP (Email), Telegram Bot Token.

## 7. Запуск і оновлення на проді

```bash
docker compose up -d --build          # перший запуск
docker compose logs -f server         # переконатися, що застосунок стартував
# релізи:
git pull && docker compose up -d --build
```

## 8. Бекап на проді
Робиться разом (див. «Бекап» нижче): `pg_dump` бази **плюс** архів тома `beauty_uploads` (фото майстрів). `pg_dump` фото не містить — у БД лише шляхи.

## Конфігурація безпеки
- **Автентифікація**: OTP — 6 цифр, у БД зберігається лише хеш (SHA256 + `CODE_SALT`), обмеження спроб і rate-limiting на `request-code`/`verify-code`/`admin-login`. JWT-ключ перевіряється на довжину ≥32 байти при старті.
- **Сесія**: короткий access-JWT + refresh-токен у httpOnly-cookie (ротація на `/api/auth/refresh`, відкликання на `/logout`).
- **Авторизація**: усе закрите за замовчуванням (`FallbackPolicy`); публічні ендпоінти мають явний `[AllowAnonymous]`.
- **CORS** — лише origins зі списку `Cors:AllowedOrigins` (у docker-стеку клієнт і API на одному origin, тож CORS фактично не задіяний).
- **Помилки**: централізований обробник повертає `{ "error": "..." }` без стектрейсу поза Development; додаються базові security headers.
- **Таймзона салону** — `Salon:TimeZone` (дефолт `Europe/Kyiv`). Слоти генеруються за «настінним» часом салону, у БД зберігаються в UTC.
- Подвійне бронювання захищене серіалізованою транзакцією в `POST /api/booking/create`.

## Можливості
- Послуги двох категорій: перукарня, манікюр
- Майстри працюють за ротацією (**тиждень через тиждень** або **2/2**); адмін може перемкнути тиждень і задати індивідуальні відхилення днів
- Бронювання: послуга → майстер → календар слотів на **28 днів (4 тижні)**
- Підтвердження запису кодом через: **SMS, Telegram, WhatsApp, Viber, Email**
- Нагадування **за 3 години** до візиту (фоновий сервіс, перевірка кожні 5 хв)
- Особистий кабінет: історія всіх записів, скасування, профіль
- Адмін-панель: CRUD послуг і майстрів, фото майстрів, графік закладу, редагування часу/статусу бронювань, пагінований список записів

## Бекап
Бекап складається з **двох** частин і робиться разом:
1. База: `docker exec beauty-db pg_dump -U beauty -d beauty > backup.sql`
2. Фото майстрів: архів тома `beauty_uploads` (у docker-стеку) або папки `server/wwwroot/uploads` (у dev).

`pg_dump` **не** містить файлів фото — у БД лише шляхи. Втрата фото дає биті посилання; UI не ламається (працює fallback на ініціали), але фото зникають безповоротно.

## Канали нотифікацій (dev vs prod)
За замовчуванням усі канали працюють у **MOCK-режимі**: код і нагадування пишуться в лог сервера та таблицю `notification_logs`, а у відповіді API (тільки в Development) повертається `devCode` (щоб тестувати без реальних SMS).

Для реальної доставки заповніть відповідні ключі (`appsettings.json`, `.env` або env-змінні):
- `Notifications:TelegramBotToken` — токен бота Telegram
- `Notifications:Twilio:*` — SMS і WhatsApp через Twilio
- `Notifications:Smtp:*` — Email
- Viber — підключається через шлюз (Infobip тощо) у `NotificationService.SendViberAsync`

## Графіки майстрів
- **Перукарі** — посмінно **2/2**: 2 дні на зміні, 2 вихідні. Тип графіка `TwoTwo`, якір — перший робочий день.
- **Майстри манікюру** — працюють **тиждень через тиждень**. Тип графіка `Weekly`, якір — понеділок робочого тижня.
- У майстра є поля `RotationType` (Weekly | TwoTwo) та `RotationAnchor` (якірна дата), а також індивідуальні відхилення днів (`MasterDayOverride`), що перекривають ротацію + графік закладу.
